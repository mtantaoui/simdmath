# AVX-512 backend

This chapter documents the AVX-512F backend. Where AVX2 widens SSE from
128 to 256 bits, AVX-512 widens it again to 512 bits and — more importantly
for transcendental code — replaces the per-lane "select-with-blendv"
control-flow pattern with a hardware **opmask** register file that drives
predication directly inside every arithmetic instruction.

The backend lives under [`src/arch/avx512/`](https://github.com/mtantaoui/simdmath/tree/main/src/arch/avx512).

## Lane counts and register types

| Type    | Underlying  | Element | Lane count | Width  |
|---------|-------------|---------|------------|--------|
| `F32x16` | `__m512`   | `f32`   | 16         | 512 b |
| `F64x8`  | `__m512d`  | `f64`   | 8          | 512 b |

Compared with AVX2 this is a 2× lane count for both precisions, processed
in a single ZMM register. The struct shape mirrors the AVX2 backend:

```rust,ignore
#[derive(Copy, Clone, Debug)]
pub struct F32x16 {
    pub(crate) size: usize,
    pub(crate) elements: __m512,
}
```

## Required CPU features

AVX-512 is a family of overlapping ISA extensions; the crate currently
requires the foundation set only:

- `avx512f` — 512-bit float and integer baseline (Skylake-X, Ice Lake,
  Tiger Lake, Sapphire Rapids on Intel; Zen 4 on AMD).

The polynomial kernels are written entirely in `avx512f`, and the FMA
intrinsics used (`_mm512_fmadd_*`, `_mm512_fnmadd_*`) are part of the
foundation set — there is no separate `+fma` flag at this width because FMA
is mandatory in AVX-512F. No `avx512vl`, `avx512dq`, or `avx512bw` is
required. Build with one of:

```bash
RUSTFLAGS="-C target-feature=+avx512f" cargo build --release
RUSTFLAGS="-C target-cpu=native"        cargo build --release   # Skylake-X+
```

Note: on some Intel client CPUs (Alder Lake, Raptor Lake) AVX-512 is
disabled at the silicon level, so `-C target-cpu=native` will *not*
activate the backend even though `avx512f` was originally implemented in
the design. Check `/proc/cpuinfo | grep avx512f` on Linux or `sysctl -a |
grep avx512f` on macOS before assuming the path is hot.

## The opmask register model

The signature change that pervades AVX-512 code is the dedicated **opmask
register file** `k0..k7`, exposed in Rust as `__mmask16` (for f32x16) and
`__mmask8` (for f64x8). Every comparison intrinsic returns one of these
mask types directly:

```rust,ignore
let is_tiny: __mmask16 = _mm512_cmp_ps_mask(abs_x, tiny, _CMP_LT_OQ);
```

This is a fundamental departure from the AVX2 `_mm256_cmp_ps` pattern,
which returns a vector of all-1/all-0 bit patterns. The mask register is
**16 bits wide** (one bit per lane) regardless of element type, and is
consumed natively by:

- `_mm512_mask_blend_*` for branchless result selection;
- `_mm512_mask_*` variants of essentially every arithmetic intrinsic, for
  per-lane predicated execution.

Concretely, the asin tail blend (compare with the AVX2 listing in the
[AVX2 chapter](./avx2.md)) reads:

```rust,ignore
let result_eq_1   = _mm512_mask_blend_ps(is_x_neg, pos_pio2, neg_pio2);
let result_small  = _mm512_mask_blend_ps(is_tiny, result_small_computed, x);
let result_ge_1   = _mm512_mask_blend_ps(is_abs_eq_1, nan, result_eq_1);
let result_valid  = _mm512_mask_blend_ps(is_abs_lt_half, result_large, result_small);
_mm512_mask_blend_ps(is_abs_ge_1, result_valid, result_ge_1)
```

Mask combination uses ordinary bitwise operators on the underlying integer:

```rust,ignore
let combined: __mmask16 = mask1 & !mask2;
```

This is shorter, faster (no vector-domain instruction), and never
contaminates the floating-point sign-bit space, which matters for `-0.0`
preservation in atan and the inverse trigs.

## Alignment

ZMM loads and stores prefer **64-byte alignment**:

```rust,ignore
impl Align<f32> for F32x16 {
    fn is_aligned(ptr: *const f32) -> bool {
        (ptr as usize).is_multiple_of(core::mem::align_of::<__m512>())
    }
}
```

`align_of::<__m512>()` is 64. As with AVX2, the backend selects between
`_mm512_load_ps` and `_mm512_loadu_ps` automatically.

## Partial loads and stores

Tail handling becomes simpler than under AVX2. The mask is computed inline
as `(1u16 << size) - 1` rather than indexed from a precomputed sign-bit
table:

```rust,ignore
unsafe fn load_partial(ptr: *const f32, size: usize) -> Self::Output {
    let mask: __mmask16 = (1u16 << size) - 1;
    Self {
        elements: _mm512_maskz_loadu_ps(mask, ptr),
        size,
    }
}
```

`_mm512_maskz_loadu_ps` zeros inactive lanes, exactly mirroring the AVX2
contract: subsequent arithmetic on padding lanes never produces spurious
infinities or NaNs.

## Advantages over AVX2

The numbers below assume identical clock and identical algorithm.

1. **2× throughput per cycle.** A 512-bit FMA executes in one cycle on the
   Skylake-X port-5 FMA unit (or two cycles on Ice Lake, where there is
   only one 512-bit FMA port instead of two 256-bit ports). For a long
   straight-line polynomial — e.g. atan's degree-11 kernel — this is
   close to a clean 2× speedup over the AVX2 path.

2. **Mask-based predication.** Removing the `blendv` instructions from the
   critical path saves one full uop per merge. atan with its 4-range
   reduction performs four blends per result; on AVX-512 these become four
   `mask_blend` instructions that retire on the same port as ordinary mask
   ops, leaving the FMA ports for actual arithmetic.

3. **32 ZMM registers.** AVX2 has 16 YMM registers; AVX-512 doubles this
   to 32 ZMM registers (`zmm0..zmm31`). For polynomial kernels with many
   pre-broadcast coefficient constants — atan's \\(aT[0..10]\\), asin's
   degree-5 numerator \\(P\_{S0..5}\\) and degree-4 denominator \\(Q\_{S1..4}\\) —
   the larger register file eliminates spill/reload traffic.

4. **Direct `f32` evaluation paths.** Some kernels that are forced to
   compute in f64 internally on AVX2 (sin, cos, tan) have enough headroom
   on AVX-512 to stay in f32, because the wider register file lets the
   kernel keep both `sin(y)` and `cos(y)` polynomial expansions live
   without spilling. The current implementation in the crate still
   promotes-to-f64 for the f32 trig kernels for ULP parity with the AVX2
   path, but the option is on the table for future work.
